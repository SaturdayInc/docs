# Nutrition Calculation

This endpoint takes an activity description and returns a fuel prescription: carbohydrate, sodium, and fluid targets, with safety guardrails applied.

```bash
POST /v1/nutrition/calculate
```

## Progressive enrichment

Saturday works with whatever data you have. More data narrows the prescription; minimal inputs still return a usable result.

### Minimal inputs

The bare minimum for a calculation:

<CodeGroup>

```python Python
import os
import requests

response = requests.post(
    "https://api.saturday.fit/v1/nutrition/calculate",
    headers={"Authorization": f"Bearer {os.environ['SATURDAY_API_KEY']}"},
    json={
        "activity_type": "run",
        "duration_min": 90,
        "athlete_weight_kg": 70,
    },
)
```

```typescript TypeScript
const response = await fetch(
  "https://api.saturday.fit/v1/nutrition/calculate",
  {
    method: "POST",
    headers: {
      Authorization: `Bearer ${process.env.SATURDAY_API_KEY}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      activity_type: "run",
      duration_min: 90,
      athlete_weight_kg: 70,
    }),
  }
);
```

</CodeGroup>

This returns a prescription with a low `confidence_score`. The numbers are based on population-level defaults for the given activity type and body weight.

### Standard inputs

Add intensity and environmental conditions:

```json
{
  "activity_type": "bike",
  "duration_min": 180,
  "intensity_level": 7,
  "athlete_weight_kg": 68,
  "thermal_stress_level": 8
}
```

Thermal stress drives the fluid and sodium targets. A 3-hour ride at high thermal stress fuels differently from the same ride in cool conditions.

### Comprehensive inputs

For exact numbers, include an athlete reference and every session input:

```json
{
  "activity_type": "bike",
  "duration_min": 300,
  "intensity_level": 8,
  "thermal_stress_level": 7,
  "meal_before_min": 120,
  "is_race": true,
  "athlete_id": "a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d"
}
```

When you include an `athlete_id`, Saturday reads that athlete's stored profile: sex, year of birth, body weight, sweat level, saltiness, carb experience, usual carb consumption, satiety level, fitness level, and fueling concerns. For an athlete linked to a Saturday account, any answer your record lacks comes from their Saturday app answers. Inline fields in the request body override the stored values for that one call.

### Session inputs

| Field | Values | What it changes |
|-------|--------|-----------------|
| `intensity_level` | 1 to 9 (1 easy, 5 moderate, 9 intervals). `lift` and `hike` use 1 to 3 | Odd levels are the Saturday app's effort bands. An even level computes halfway between the levels on either side. An omitted level computes as 5 (2 for `lift` and `hike`) |
| `thermal_stress_level` | 1 (cold, dry) to 9 (hot, humid) | Fluid and sodium most of all |
| `meal_before_min` | Minutes since the athlete's last carb-rich meal | More than 180 plans a fasted start: a 20-minute pre-load before the session and more during it. 180 or fewer plans a fed start |
| `is_race` | `true` or `false` | A race is planned at a higher tolerance for eating, which raises carbohydrate for most athletes |

All four belong on every call. An omitted one is an unanswered input: the session still computes (at effort 5, or 2 for `lift` and `hike`; heat 5; fed; training), but the answer comes back as ranges even for a complete profile, with the input named in `precision.missing_fields`. `precision.message` names the athlete's missing profile answers apart from the session inputs your request left out, and `precision.onboarding` appears only when profile answers are missing, since a session input is yours to send.

An `athlete_id` your account does not hold is refused with `404` and code `athlete_not_found`; leave `athlete_id` out for a range estimate.

The request may carry only the fields on this page. Any other field, at any depth, is refused with `400` and code `unsupported_field`, `param` naming it, and the message naming the field it was probably meant to be: `meal_before_mins` answers `Did you mean "meal_before_min"?`. A field spelled the way the athlete or activity request spells it gets that request's spelling: `weight_kg` (send `athlete_weight_kg`), `year_of_birth` (send `age`), `is_race_event` (send `is_race`), `type` (send `activity_type`), `duration` (send `duration_min`) and `settings` (send the profile fields at the top level, or an `athlete_id`). See [Error Handling](/error-handling#a-field-the-request-does-not-take).

## Understanding the response

This example shows an exact full-tier response with complete inputs. Teaser responses and incomplete full-tier profiles contain range fields instead, even when the request succeeds.

```json
{
  "tier": "full",
  "carb_g_per_hr": 72,
  "sodium_mg_per_hr": 800,
  "fluid_ml_per_hr": 750,
  "total_carb_g": 360,
  "total_sodium_mg": 4000,
  "total_fluid_ml": 3750,
  "safety": {
    "max_safe_fluid_ml_per_hr": 1500,
    "max_safe_sodium_mg_per_hr": 3000,
    "confidence_score": 1,
    "requires_human_review": false,
    "warnings": [],
    "not_instructions": true
  },
  "attribution": {
    "text": "Powered by Saturday",
    "logo_url": "https://saturday.fit/logo.png",
    "link": "https://saturday.fit",
    "required": true
  },
  "precision": {
    "profile_complete": true
  }
}
```

### Per-hour figures

The per-hour figures are the ones the Saturday app shows on its fueling card, so your athletes see the same numbers in both places:

- Whole numbers. Sodium and fluid round to 10.
- Carbohydrate per hour stops at the athlete's carb ceiling.
- A fasted start spreads the totals over the session plus its 20-minute pre-load. A 60-minute fasted run with `total_carb_g: 45` shows `carb_g_per_hr: 34` (45 over 80 minutes).
- A session of 20 minutes or less shows at most 600 mL of fluid per hour.

The `total_*` fields are the amounts for the whole session, the pre-load included.

### Confidence score

The `safety.confidence_score` (0.0-1.0) is read from the width of the band: 1.0 when every profile field and every activity input for the call is answered (on the full tier the numbers are then exact), lower as unanswered fields widen the band. Activity inputs weigh heavily: a call that omits `intensity_level` and `thermal_stress_level` can score 0 with a complete stored profile. `precision.missing_fields` tells you which answers would raise it.

| Range | Meaning |
|-------|---------|
| 0.8-1.0 | Complete or near-complete inputs; at 1.0 a full-tier response carries exact numbers |
| 0.5-0.8 | Several profile fields still defaulted |
| 0.0-0.5 | Mostly population defaults; the band is at or near its cap |

## Comparing across conditions

To compare fueling across different conditions (a cool morning against a hot afternoon, say), call `POST /v1/nutrition/calculate` once per scenario and diff the results yourself, or use `POST /v1/nutrition/calculate/batch` to submit up to 50 scenarios in a single request. Each scenario in a batch debits your quota individually.

<Note>
  Two prescription shapes. The `calculate` endpoints return a flat response (`carb_g_per_hr`, `sodium_mg_per_hr`, … with a nested `safety` block). The stored-prescription read (`GET /v1/athletes/{id}/activities/{id}/prescription`) returns a wrapped response: `{ "prescription": { … }, "safety": { … } }`. Read the fields according to the endpoint you called.
</Note>

## Calculation timing

Every engine run carries a deliberate computation window, the same one athletes see in the Saturday app. Size your loading state around it:

- **Single calculation** (`POST /v1/nutrition/calculate`, `POST .../activities/{id}/calculate`): roughly 1 to 3 seconds, scaling with activity duration and shorter at low intensity. Recalculating an activity that has a prescription takes about half as long.
- **Batch** (`POST /v1/nutrition/calculate/batch`): each scenario adds about half a single calculation's time. The response headers arrive immediately with `X-Batch-Estimated-Ms`, the expected total processing time, so you can size a progress indicator before the body lands. The completed body includes `estimated_ms` and `elapsed_ms`.
- **Estimate without calculating:** send the same batch payload with `"estimate_only": true` to get `estimated_ms` back immediately, with no calculations run and no quota debited. Useful when your HTTP client can't read streamed headers early.
- **Reads are instant.** Fetching a stored prescription (`GET .../prescription`) carries no computation window.

<Tip>
  Fill the window with a specific state, such as "calculating your fueling plan", rather than a bare spinner or a frozen screen.
</Tip>

## Teaser vs. full responses

Responses depend on the athlete's Saturday subscription status:

- **Subscribed athletes with complete inputs** get exact numbers: `"carb_g_per_hr": 72`
- **Subscribed athletes with incomplete inputs** get ranges and a `precision` object naming the missing fields
- **Free/teaser athletes** get ranges: `"carb_range_g_per_hr": "60-90"`

Teaser ranges are bucketed to a fixed grid, 30 g/hr for carbohydrate and 500 units/hr for sodium and fluid, so the same underlying number always lands in the same bucket.

See [Freemium Model](/guides/freemium-model) for implementation details.

## Safety

Every calculation response includes a `safety` block, on every tier. See [Safety](/guides/safety) for the fields, the guardrails behind them, and what you are required to display.

<Warning>
  Safety data is never gated behind subscription status. Teaser responses carry the same safety block as full ones.
</Warning>

## Supported activity types

| Type | Key | Notes |
|------|-----|-------|
| Running | `run` | Road, trail, track |
| Cycling | `bike` | Road, gravel, mountain |
| Swimming | `swim` | Pool, open water |
| Rowing | `row` | On-water, ergometer |
| Skiing | `ski` | Cross-country, classic, skate |
| Hiking | `hike` | Long-duration, variable intensity |
| Weightlifting | `lift` | Strength training |

These seven sports, with `brick` and `triathlon` ([below](#bricks-and-triathlons)), are the complete set, accepted in any letter case. Any other `activity_type` is refused with `400` and code `invalid_value`, on calculate, on each batch scenario and on activity create, so map your own sport names first: `POST /v1/infer/activity-type` does it from a title. `GET /v1/activity-types` returns the seven sports with descriptions in `activity_types`, and `brick` and `triathlon` with the rules for their legs in `linked_session_types`. An optional `?activity_type=` narrows both lists to the one type named, so you can validate a single key.

## Bricks and triathlons

A brick (two or more sports back to back) or a triathlon is one session made of legs. Send it as one request with `activity_type` `brick` or `triathlon` and `legs`, never as one request per leg: Saturday computes it as the Saturday app does, as one continuous effort, so its totals are larger than its legs calculated separately.

```json
{
  "athlete_id": "a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d",
  "activity_type": "brick",
  "meal_before_min": 120,
  "is_race": false,
  "legs": [
    {"activity_type": "bike", "duration_min": 90, "intensity_level": 6, "thermal_stress_level": 6},
    {"activity_type": "run", "duration_min": 30, "intensity_level": 7, "thermal_stress_level": 6}
  ]
}
```

| Rule | Detail |
|------|--------|
| Legs | 2 to 10, in the order they are done |
| Each leg | `activity_type` (one of the seven sports), `duration_min` (5 to 2160), `intensity_level` (1 to 9; `lift` and `hike` 1 to 3, a higher value computing as 3) and `thermal_stress_level` (1 to 9), all four required |
| `duration_min` | The legs' total, at most 2160. Leave it out, or send that total |
| `intensity_level`, `thermal_stress_level` | On the legs only. At the top level they are refused with `400` `invalid_value` |
| `meal_before_min`, `is_race` and profile fields | At the top level, for the whole session |

A brick or triathlon without `legs` is refused with `400` `missing_field` on `legs`, and `legs` on a single sport with `400` `invalid_value`. A leg's own error names its path, such as `legs[1].duration_min`.

An answer with exact numbers carries `legs`: each leg's share, in the order sent, as the Saturday app's leg cards show it.

```json
{
  "tier": "full",
  "carb_g_per_hr": 70,
  "sodium_mg_per_hr": 400,
  "fluid_ml_per_hr": 600,
  "total_carb_g": 140,
  "total_sodium_mg": 800,
  "total_fluid_ml": 1200,
  "legs": [
    {"duration_min": 90, "total_carb_g": 110, "total_sodium_mg": 600, "total_fluid_ml": 900, "carb_g_per_hr": 73, "sodium_mg_per_hr": 400, "fluid_ml_per_hr": 600},
    {"duration_min": 30, "total_carb_g": 30, "total_sodium_mg": 200, "total_fluid_ml": 250, "carb_g_per_hr": 60, "sodium_mg_per_hr": 400, "fluid_ml_per_hr": 500}
  ],
  "precision": {"profile_complete": true}
}
```

The session's per-hour figures are over the legs' total minutes. A leg's per-hour figures are over its own minutes, and the first leg of a fasted start adds the 20-minute pre-load. The legs' totals add up to the session's totals before the session's own rounding. An answer with ranges carries no leg figures.

Bricks and triathlons work the same way in [batches](/guides/batch-operations), on [stored activities](/guides/activities#bricks-and-triathlons) and in [prep](/guides/prep-and-products). Product fit and compare size a product for a single sport. Bricks and triathlons are for requests made with a partner API key; an athlete's own assistant connected through the Saturday connector plans single sports.

<Note>
Every calculation response carries a `precision` object: `profile_complete`, `missing_fields`, and an onboarding invite. Exact numbers require a complete fueling profile; an incomplete one gets a band instead. See [Athlete Onboarding](/guides/onboarding).
</Note>
