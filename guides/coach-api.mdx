# Coach API

The Coach API exposes a coach's Saturday surface over a coach-scoped REST API, and over an [MCP connector](/guides/coach-connector): the per-athlete fueling rollup, AI reports, the roster's needs-attention markers, the notification and alerting settings, and a read-only view of the coach's billing.

It is built for a coach who wants to automate fueling monitoring: read who needs attention, pull a report, and configure alert rules and digests across a whole roster programmatically.

<Note>
  **Tier requirements.** Coach endpoints require the Pro Coach tier or above (Pro Coach, Head Coach, Business, Enterprise), and the tier is checked on every request. Two further gates sit above that line: minting a coach API key in the portal requires the Business or Enterprise tier, and webhook *delivery* requires Business or Enterprise. A Pro Coach or Head Coach therefore reaches the whole surface through the OAuth connector, and reaches it through an API key only if someone on a Business or Enterprise plan minted one.
</Note>

<Note>
  **When a tier lapses.** On an OAuth token, the coach tools stop resolving and coach endpoints return `404`, while the token keeps working for the coach's athlete data. There is no error and no separate "downgrade" call. A coach API key has no athlete-self facet to fall back to, so the request is refused with `403 coach_tier_required`.
</Note>

## Authentication

Two ways to authenticate as a coach. Both resolve to the same coach identity and roster.

| Method | Token | Best for |
|--------|-------|----------|
| **Coach API key** | `cp_live_…` / `cp_test_…` (Bearer) | Scripts, automations, server-to-server |
| **OAuth2 (coach scopes)** | OAuth2 access token (Bearer) | The Claude.ai connector / user-delegated apps |

Coach API keys are minted in the [coach portal](https://coach.saturday.fit) under **[Admin → API Keys](https://coach.saturday.fit/admin/api-keys)**. Pass the key as a Bearer token:

```bash
curl -H "Authorization: Bearer cp_live_..." https://api.saturday.fit/v1/coach/roster
```

OAuth2 coaches use the [connector OAuth flow](/guides/oauth2) with coach scopes (`coach:roster`, `coach:reports`, `coach:alerts`, `coach:webhooks`). Because a coach is also an athlete, the same OAuth token acts as an athlete-self token on `/v1/athletes/*`.

## Scopes and capabilities

A coach token or key carries scopes, and each scope confers one or more of five capabilities. A route is reachable only when the credential confers the capability it requires; otherwise it returns the uniform `404`.

| Capability | OAuth scope | Endpoints |
|------------|-------------|-----------|
| Read roster | `coach:roster` | `GET /v1/coach/roster`, `GET /v1/coach/athletes/{athlete_uid}/fueling-rollup`, `GET /v1/coach/athletes/{athlete_uid}/sessions/{activity_id}` |
| Read reports | `coach:reports` | `GET /v1/coach/roster/digest`, `GET /v1/coach/athletes/{athlete_uid}/report` |
| Configure alerts and reports | `coach:alerts` | `GET` and `PUT /v1/coach/config/notification-rules`, `POST /v1/coach/config/preset`, `GET` and `PUT /v1/coach/config/report-settings` |
| Manage webhooks | `coach:webhooks` | `GET` and `POST /v1/coach/webhooks`, `DELETE /v1/coach/webhooks/{id}`, `POST /v1/coach/webhooks/{id}/disable`, `POST /v1/coach/webhooks/{id}/enable` |
| Read billing | none (API keys only) | `GET /v1/coach/billing/seat-state`, `GET /v1/coach/billing/ledger`, `GET /v1/coach/billing/tier-status`, `GET /v1/coach/billing/connect/summary`, `GET /v1/coach/billing/connect/earnings`, `GET /v1/coach/billing/connect/transactions`, `GET /v1/coach/billing/connect/arrangements` |

Reading config takes the same capability as writing it: a credential without it gets `404` from `GET /v1/coach/config/notification-rules` as well as from `PUT`.

An API key's scopes, chosen when the key is minted in the portal, map onto the same capabilities. Billing is reachable with an API key only; the OAuth connector has no billing scope.

| API-key scope | Read roster | Read reports | Configure alerts and reports | Manage webhooks | Read billing |
|---------------|-------------|--------------|------------------------------|-----------------|--------------|
| `roster:read` | Yes | | | | |
| `roster:write` | Yes | | Yes | | |
| `reports:read` | | Yes | | | |
| `org:read` | Yes | Yes | | | |
| `org:write` | Yes | Yes | Yes | | |
| `org:admin` | Yes | Yes | Yes | Yes | |
| `webhooks:manage` | | | | Yes | |
| `billing:read` | | | | | Yes |
| `*` (keys minted before scoped keys existed) | Yes | Yes | Yes | Yes | |

Scopes union: a key with several scopes holds every capability any of them confers, and nothing more. `roster:write` also reads the roster, since configuring alerts against a roster means seeing it. `roster:read` alone does not open the report routes; add `reports:read`, or pick `org:read` or higher. Billing is never bundled: only a key that carries `billing:read` reads billing, whatever else it carries, so a key built for roster automation cannot see money unless the coach ticked that scope.

The portal offers each coach only the scopes their role and plan can mint. `webhooks:manage` needs a coaching role and the Pro Coach plan or higher; `org:admin` needs an organization owner or admin role; `billing:read` needs the role that sees the portal's Billing pages. A solo coach on Business mints everything except `org:admin`.

<Warning>
  **Roster confinement.** Every `{athlete_uid}` you pass is checked against your roster. An athlete who isn't on your roster, and an athlete who doesn't exist, both return `404 resource_not_found`. The two cases are indistinguishable, so the API never reveals whether an athlete exists.
</Warning>

## Reads

### List the roster

`GET /v1/coach/roster` returns every athlete you coach, each with a needs-attention summary over the look-back window.

```bash
curl -H "Authorization: Bearer cp_live_..." \
  "https://api.saturday.fit/v1/coach/roster?window=14"
```

| Query param | Values | Default |
|-------------|--------|---------|
| `window` | `7`, `14`, `30` | your configured report window |

```json
{
  "coach_uid": "coach_abc",
  "window": 14,
  "athletes": [
    {
      "athlete_uid": "ath_123",
      "flagged": true,
      "flagged_count": 2,
      "top_reasons": ["Sodium 57%", "1 symptom"],
      "session_count": 6
    }
  ]
}
```

The markers come from Saturday's single shared concern definition, so they match the coach portal table and the digest exactly. An athlete who fueled well shows `flagged: false`.

### Roster digest (flagged-only)

`GET /v1/coach/roster/digest` returns the same data for athletes who crossed a concern bar this window, most-flagged first. Athletes who did not cross a bar are omitted, which is what makes this the useful call on a large roster.

```json
{
  "coach_uid": "coach_abc",
  "window": 7,
  "flagged_count": 3,
  "total_count": 48,
  "flagged": [
    {
      "athlete_uid": "ath_123",
      "flagged": true,
      "flagged_count": 2,
      "top_reasons": ["Sodium 57%", "1 symptom"],
      "session_count": 6
    }
  ]
}
```

`flagged` carries the same entry shape as `GET /v1/coach/roster` above, ordered most-flagged first. `flagged_count` counts the entries in it; `total_count` counts the whole roster.

### Per-athlete fueling rollup

`GET /v1/coach/athletes/{athlete_uid}/fueling-rollup` returns one athlete's in-window sessions (the same table the portal renders) plus the concern summary and the resolved cutoffs that produced the markers.

| Query param | Values | Default |
|-------------|--------|---------|
| `window` | `7`, `14`, `30` | your configured window |
| `focus` | `worst`, `rolling`, `key` | your configured focus |

```json
{
  "athlete_uid": "ath_123",
  "window": 14,
  "focus": "rolling",
  "sessions": [
    {
      "activity_id": "act_789",
      "date_millis": 1749480000000,
      "type": "ride",
      "duration_min": 210,
      "is_race": false,
      "carb_pct": 0.82,
      "sodium_pct": 0.57,
      "fluid_pct": 0.94,
      "consumed_carb_g": 172,
      "consumed_sodium_mg": 1140,
      "consumed_fluid_ml": 2350,
      "user_rating": 3,
      "symptoms": { "cramp": 1 },
      "sleep_hours": 6.5
    }
  ],
  "concern": {
    "flagged": true,
    "flagged_count": 2,
    "top_reasons": ["Sodium 57%", "1 symptom"]
  },
  "settings_resolved": {
    "report_window_days": 14,
    "report_focus": "rolling",
    "concern_carb_cutoff": 0.7,
    "concern_sodium_cutoff": 0.7,
    "concern_fluid_cutoff": 0.7,
    "hyponatremia_fluid_min": 0.9,
    "hyponatremia_sodium_max": 0.5
  }
}
```

The session object above is abbreviated. Each entry also carries the as-used and suggested prescription totals, prep fidelity, leftover reuse, report source and completeness, intensity, the profile snapshot, opaque `vessel_reports` and `weather` maps, and the derived `adherence_vs_suggested`, `dial_down_gap`, and `per_hour` triples.

The adherence fractions are uncapped, so a value above `1.0` is genuine over-consumption rather than an error. Every missing value stays `null`, never `0`, and an absent `symptoms` key is not a zero.

### AI report

`GET /v1/coach/athletes/{athlete_uid}/report` returns the AI-generated fueling report: a third-person narrative grounded only in the athlete's numbers, plus the structured concern summary behind it, so an agent can quote the prose or compute on the data.

| Query param | Values | Notes |
|-------------|--------|-------|
| `window` | `7`, `14`, `30` | look-back |
| `focus` | `worst`, `rolling`, `key` | report focus |
| `refresh` | `true` | force regeneration even if a cached report exists |
| `format` | `pdf` | return the report as a downloadable PDF instead of JSON |

```json
{
  "athlete_uid": "ath_123",
  "window": 14,
  "focus": "rolling",
  "narrative": "Over the last two weeks, this athlete …",
  "concern": {
    "flagged": true,
    "flagged_count": 2,
    "top_reasons": ["Sodium 57%", "1 symptom"]
  },
  "generated_at": 1749500000000,
  "latest_session_ms": 1749480000000,
  "from_cache": true
}
```

Served from cache unless a newer session has landed or `refresh=true`.

### Session detail

`GET /v1/coach/athletes/{athlete_uid}/sessions/{activity_id}` drills into one session: the full per-session projection (planned-vs-actual fueling, symptoms, vessel reports, weather, sleep) plus the concern markers that session crossed.

```json
{
  "athlete_uid": "ath_123",
  "session": { "activity_id": "act_789", "date_millis": 1749480000000, "type": "ride", "sodium_pct": 0.57 },
  "markers": [
    { "kind": "under_fuel", "nutrient": "sodium", "reason": "Sodium 57%" },
    { "kind": "symptom", "reason": "1 symptom" }
  ]
}
```

`session` is the same projection as a rollup entry, abbreviated here. An activity outside the athlete's history returns `404`.

## Configuration

Most of the Coach API is a configuration surface. It writes the same alert-rule and report-settings model the portal reads: channels, triggers, per-trigger thresholds, the overall/group/athlete scope hierarchy, cadence, quiet hours, two-trigger combinators, and AI-report defaults. The portal UI and the API are two views of one config model.

<Info>
  **Scope precedence.** Config applies at one of three scopes: `overall` (the whole roster), `group` (a coach group), or `athlete` (one athlete). When resolving what an athlete sees, the most specific scope wins (athlete over group over overall). `scope_id` is required for `group` and `athlete`, and omitted for `overall`.
</Info>

### Notification rules

`GET /v1/coach/config/notification-rules?scope=overall` reads the rules set at exactly that scope, not the merged resolution. A scope with no rules returns an empty rule set.

`PUT /v1/coach/config/notification-rules` replaces the rule set at a scope and answers `{"ok": true, "scope": "..."}`. It is an idempotent upsert: re-running with the same body is a no-op, so no per-request idempotency key is needed. A malformed rule set (an unknown trigger, channel, or cadence, a bad combinator, or quiet hours enabled without valid `HH:MM` times) returns `400 invalid_config`.

```bash
curl -X PUT https://api.saturday.fit/v1/coach/config/notification-rules \
  -H "Authorization: Bearer cp_live_..." \
  -H "Content-Type: application/json" \
  -d '{
    "scope": "group",
    "scope_id": "grp_elite",
    "rules": {
      "notification_rules": {
        "under_fuel": { "enabled": true, "channels": ["email", "webhook"], "cadence": "realtime", "urgent_threshold": 0.6 },
        "hyponatremia_pattern": { "enabled": true, "channels": ["push"], "cadence": "realtime" }
      },
      "combinators": [
        { "trigger_a": "under_fuel", "trigger_b": "symptom", "channel": "push", "cadence": "realtime" }
      ],
      "quiet_hours": { "enabled": true, "start": "22:00", "end": "06:00", "tz": "America/Denver" }
    }
  }'
```

**Triggers:** `under_fuel`, `symptom`, `low_rating`, `hyponatremia_pattern`, `dial_down`, `sleep_trend`, `went_quiet`.

**Channels:** `in_portal`, `email`, `push`, `webhook`.

**Cadence:** `realtime` (sent as it happens) or `digest` (bundled into one daily item per athlete).

**Thresholds** are fractions of the as-used prescription. `urgent_threshold` sets the urgent band (`0.6` means below 60%). `amber_threshold` is optional and decouples this trigger's marker line from the shared cutoff; omit it to use the resolved concern cutoff.

**Combinators** are bounded two-trigger ANDs: both legs must be markers on the same session ("sodium short AND a cramp"). Exactly two distinct session-level triggers (`under_fuel`, `symptom`, `low_rating`, `hyponatremia_pattern`, `dial_down`), with no OR, NOT, or nesting. `sleep_trend` and `went_quiet` are window-level and cannot be combined.

### Presets

`POST /v1/coach/config/preset` applies a named starting point at a scope, which you can then tweak rule by rule. It answers `{"ok": true, "preset": "..."}`; an unknown preset returns `400 invalid_config`.

```bash
curl -X POST https://api.saturday.fit/v1/coach/config/preset \
  -H "Authorization: Bearer cp_live_..." \
  -H "Content-Type: application/json" \
  -d '{ "scope": "overall", "preset": "balanced" }'
```

| Preset | Behavior |
|--------|----------|
| `hands_off` | in-portal only, no pings |
| `balanced` | core concerns on email, daily digest |
| `hands_on` | all triggers, real-time urgent push |

### AI-report & concern settings

`GET /v1/coach/config/report-settings?scope=overall` reads the report window/focus defaults and any overridden concern cutoffs set at exactly that scope. `PUT /v1/coach/config/report-settings` upserts them. Unset fields fall through to the broader scope.

| Field | Values |
|-------|--------|
| `ai_report_window_days` | `7`, `14`, `30` |
| `ai_report_focus` | `worst`, `rolling`, `key` |
| `concern_carb_cutoff`, `concern_sodium_cutoff`, `concern_fluid_cutoff` | a fraction in `(0,1]` |
| `hyponatremia_fluid_min`, `hyponatremia_sodium_max` | a fraction in `(0,1]` |

```bash
curl -X PUT https://api.saturday.fit/v1/coach/config/report-settings \
  -H "Authorization: Bearer cp_live_..." \
  -H "Content-Type: application/json" \
  -d '{
    "scope": "athlete",
    "scope_id": "ath_123",
    "settings": {
      "ai_report_window_days": 30,
      "ai_report_focus": "key",
      "concern_sodium_cutoff": 0.65
    }
  }'
```

<Warning>
  **Athlete data is read-only.** The Coach API never writes an athlete's fueling data, debriefs, or prescriptions. A coach configures only the coach's alerts, report settings, and thresholds.
</Warning>

## Webhooks

A webhook is another delivery channel on the alerts you configure (`"channels": ["webhook"]`). Register an endpoint, then select `webhook` as a channel on any rule.

<Note>
  Webhook delivery requires the Business or Enterprise tier. Registration succeeds at Pro Coach and Head Coach, but nothing is delivered until the tier qualifies. The tier is checked on every delivery, so delivery stops as soon as it drops.
</Note>

`POST /v1/coach/webhooks` registers an endpoint and answers `201` with the signing secret, once.

```bash
curl -X POST https://api.saturday.fit/v1/coach/webhooks \
  -H "Authorization: Bearer cp_live_..." \
  -H "Content-Type: application/json" \
  -d '{ "url": "https://my-system.example.com/saturday", "events": ["concern.detected", "athlete.needs_attention"] }'
```

```json
{
  "id": "wh_abc",
  "coach_uid": "coach_abc",
  "url": "https://my-system.example.com/saturday",
  "events": ["concern.detected", "athlete.needs_attention"],
  "active": true,
  "created_at": 1749500000000,
  "updated_at": 1749500000000,
  "fail_count": 0,
  "secret": "whsec_…"
}
```

<Warning>
  `secret` appears in this response and never again. `GET /v1/coach/webhooks` omits it, and there is no endpoint that re-reads it. Store it when you register, or delete the endpoint and register a new one to get a fresh secret.
</Warning>

| Method · path | Action |
|---------------|--------|
| `GET /v1/coach/webhooks` | list endpoints (secrets never returned) |
| `POST /v1/coach/webhooks` | register (secret returned once) |
| `DELETE /v1/coach/webhooks/{id}` | delete an endpoint |
| `POST /v1/coach/webhooks/{id}/disable` | disable (stop delivery, keep the endpoint) |
| `POST /v1/coach/webhooks/{id}/enable` | re-enable |

**Event types:** `concern.detected` and `athlete.needs_attention`, which an empty `events` list subscribes you to (`["*"]` subscribes to every coach event), plus `coach.message.sent`, which is opt-in and fires only for Enterprise coaches, mirroring messages the coach sends from the portal. An unknown event name fails registration with `400`. The URL must be public `https` on the standard port; internal, metadata, and loopback URLs are rejected at registration.

Each delivery is a `POST` carrying the event name in `X-Saturday-Event-Type` and an HMAC-SHA256 signature in `X-Saturday-Signature` (`t=<unix seconds>,v1=<hex>`) computed with the secret returned at registration. See [Webhooks](/guides/webhooks) for verifying it. The body is the event, with `data` shaped per event type:

```json
{
  "type": "concern.detected",
  "created_at": 1749500000000,
  "coach_uid": "coach_abc",
  "data": {
    "coach_uid": "coach_abc",
    "athlete_uid": "ath_123",
    "concern_type": "under_fuel",
    "severity": "urgent",
    "session_ref": "act_789",
    "nutrient": "sodium",
    "value_pct": 0.42,
    "threshold_pct": 0.6,
    "detected_at": 1749480000000,
    "evaluation": "urgent_scanner"
  }
}
```

Each event is delivered once. A non-2xx response or a connection failure is recorded and counts toward the endpoint's `fail_count`; a 2xx resets it, and the endpoint is disabled automatically after 15 consecutive failures. Re-enabling it clears the count.

## Billing (read-only)

A key carrying `billing:read` reads the figures the portal's Billing pages show, for the coach who minted the key: their seats, their financial ledger, their platform subscription, and their Stripe Connect earnings. Every amount is an integer number of cents in the row's `currency` (`usd`), and every timestamp is Unix milliseconds, the same values the portal renders. There is no billing write scope: covering athletes, changing plans, refunds and payouts stay in the portal.

A coach with no organization reads their figures on every endpoint. A coach with no Stripe Connect account gets a null account and zero totals from the Connect endpoints, never an error.

### Seat state

`GET /v1/coach/billing/seat-state` returns the live seat picture from the roster header: the funding tier, the included allotment and how much of it is used, the coach-paid count and what covering one more athlete costs now. Pass `?org_id=` to read the organization's seats as payer; only the coach's organization is accepted, and any other value answers `404`.

```bash
curl -H "Authorization: Bearer cp_live_..." \
  https://api.saturday.fit/v1/coach/billing/seat-state
```

```json
{
  "tier": "business",
  "included_total": 50,
  "included_used": 12,
  "coach_paid_count": 0,
  "next_athlete_price_cents": 0,
  "volume_tier": 0,
  "volume_discount_pct": 0,
  "total_monthly_cents": 0,
  "is_fair_use": true
}
```

| Query param | Values | Default |

| `limit` | `1` to `200` | `50` |
| `cursor` | the `next_cursor` from the previous page | first page |

```bash
curl -H "Authorization: Bearer cp_live_..." \
  "https://api.saturday.fit/v1/coach/billing/ledger?view=inflows&limit=50"
```

```json
{
```

## Athlete identity

Coach API responses identify each athlete by Saturday UID, the same identifier the portal uses, and carry their fueling data exactly as the coach sees it there: sessions, symptoms, ratings, sleep, and the calculator profile snapshot. The coach owns the coaching relationship, so the API applies no de-identification; identity levels belong to the portal's export feature. Handling that personal data downstream is your responsibility. See the [data policy](/guides/data-policy).

## Rate limits

Coach requests draw from the coach's bucket: 50 requests per second with a burst of 500, the same whether the call is a REST request to `/v1/coach/*` on either credential or a coach tool used in chat through the connector. Coach tools in chat also pass the connector's shared bucket, as every connector call does. The billing reads share the coach bucket with the rest of the coach surface. Athlete tools used in the same chat, and a coach token's athlete-self calls on `/v1/athletes/*`, keep the per-athlete bucket that applies to every athlete-delegated caller. A roster pull or digest is one request whatever the roster size. Every response carries the rate-limit headers and a `429` carries `Retry-After`; see [rate limiting](/rate-limiting).

A coach API key reaches `/v1/coach/*` only; on any other endpoint it is refused with `403 insufficient_scope`.
