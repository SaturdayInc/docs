# Freemium Model

Saturday's API is free for partners to integrate. The monetization happens at the athlete level: athletes subscribe to Saturday for full-precision nutrition data.

```
Partner integrates (free) -> Athletes see teasers (free) -> Athletes subscribe for precision
```

## Teaser vs. full comparison

| | Teaser (free) | Full (subscribed) |
|---|---|---|
| **Carbohydrates** | Range: `"carb_range_g_per_hr": "60-90"` | Exact: `"carb_g_per_hr": 62` |
| **Hydration** | Range: `"fluid_range_ml_per_hr": "500-1000"` | Exact: `"fluid_ml_per_hr": 620` |
| **Sodium** | Range: `"sodium_range_mg_per_hr": "200-500"` | Exact: `"sodium_mg_per_hr": 490` |
| **Products** | Category only ("gel") | Specific products + schedule |
| **Safety metadata** | Full | Full |
| **Confidence score** | Shown | Shown |

<Note>
  **Safety is never gated.** Both teaser and full responses include complete safety metadata. Safety information is always free.
</Note>

## Detecting response type

Both teaser responses and incomplete full-tier profiles carry range fields. Choose the number display from those fields; use `tier` separately to decide whether to show the subscription CTA. Exact zero values may be omitted, so the exact branch defaults them to zero. An activity calculation nests its exact numbers under `prescription`, so read the number fields from there when it is present.

<CodeGroup>

```python Python
data = response.json()
numbers = data.get("prescription", data)

if "carb_range_g_per_hr" in numbers:
    show_range(numbers["carb_range_g_per_hr"])
    show_range(numbers["sodium_range_mg_per_hr"])
    show_range(numbers["fluid_range_ml_per_hr"])
else:
    show_exact(numbers.get("carb_g_per_hr", 0))
    show_exact(numbers.get("sodium_mg_per_hr", 0))
    show_exact(numbers.get("fluid_ml_per_hr", 0))

if data["tier"] == "teaser":
    show_upgrade_cta(data["subscription_cta"]["subscribe_url"])
```

```typescript TypeScript
const data = await response.json();
const numbers = data.prescription ?? data;

if (numbers.carb_range_g_per_hr !== undefined) {
  showRange(numbers.carb_range_g_per_hr);

  showRange(numbers.fluid_range_ml_per_hr);
} else {
  showExact(numbers.carb_g_per_hr ?? 0);
  showExact(numbers.sodium_mg_per_hr ?? 0);
  showExact(numbers.fluid_ml_per_hr ?? 0);
}

if (data.tier === "teaser") {
  showUpgradeCTA(data.subscription_cta.subscribe_url);
}
```

</CodeGroup>

## Full-precision trial

An athlete-scoped calculation with real profile or optional activity inputs starts a **14-day trial of full-tier responses: 15 calls on the first UTC day (exploration allowance), then 5 calls per athlete per UTC day, and at most 42 in all**. Zero-data calls do not start the trial. Complete inputs are still required for exact numbers. During the trial, full responses carry trial metadata so you can build countdown UX:

```json
{
  "tier": "full",
  "tier_source": "trial",
  "trial_ends_at": 1768063200,
  "trial_calls_remaining_today": 3,
  "carb_g_per_hr": 62
}
```

`trial_ends_at` is a Unix timestamp in seconds, like every other time a partner key receives.

Over the daily cap, responses degrade to teaser ranges (never an error) and include `trial_cap_reached: true` plus a human-readable `trial_cap_note` you can surface directly to the athlete. It carries the apology and the reason. Batch scenarios debit the cap individually. After 14 days, or once the trial has given its 42 exact answers, responses are teaser tier until the athlete subscribes.

### Trial bounds per key

Three more bounds keep the trial to real athletes. None is an error: the answer comes back in teaser ranges with a flag and a `trial_note` you can show the athlete as it stands.

- **New trials per day.** A key starts at most 50 new trials per UTC day (5 for a key that comes with a Saturday plan). An athlete past that gets ranges with `trial_start_deferred: true`, and their trial starts on a later day. Athletes already in their trial are not affected. Rolling out to a large roster? Email api@saturday.fit and we raise it for your key.
- **Profiles per trial athlete.** One trial athlete's exact numbers cover up to 3 distinct profiles over the trial: their first, plus two changes. Small day-to-day weight changes do not count as changes. A fourth profile gets ranges with `trial_profile_limit_reached: true`; the earlier profiles stay exact. Subscribed athletes have no such bound.
- **Exact answers per trial.** One athlete's trial gives at most 42 exact answers in all, however the days fall. The next answer comes back in ranges with `trial_answers_used_up: true`, and its `trial_note` says a Saturday subscription gives exact numbers.

`GET /v1/partner` shows your key's numbers under `rate_limits`: `trial_days`, `trial_answers`, `trial_starts_per_day` and `trial_profiles_per_athlete`.

## Subscription flow

When an athlete wants full precision:

1. Your app shows teaser data with the upgrade CTA
2. Athlete taps the upgrade link (`subscribe_url` from the `subscription_cta`). For athlete-scoped requests it carries a signed token (`pst`) identifying *which* athlete is upgrading
3. The athlete lands on Saturday's checkout page (partner-branded), pays via Stripe, and is sent back toward your app
4. Saturday writes the link and fires the `subscription.created` webhook, and the athlete's next API call returns full precision

Saturday manages the subscription and the payment. Two important details:

- **The unlock requires athlete-scoped requests.** Only CTAs minted from requests that included an `athlete_id` carry the `pst`; identity-less CTAs are attribution-only and cannot auto-unlock anyone.
- **Subscribed Saturday users are never double-charged.** If the athlete has an active Saturday subscription, checkout links their account to your athlete instead of charging, and `subscription.created` fires with `source: "existing_subscription_linked"`.

### Checking entitlement

`GET /v1/athletes/{id}` returns a computed `subscription_status` field (`full`, `trial`, or `teaser`) for polling after checkout-return or support lookups.

### Return-to-app handoff

Give Saturday a `return_url` (https or deep link) at partner onboarding and the post-payment success page shows a "Back to your app" button, so athletes land back in your product with full precision flowing.

### Automatic linking by email

Some paying Saturday athletes never touch your subscribe CTA: they subscribed **inside the Saturday app** (Apple/Google in-app purchase) or on saturday.fit before joining your platform. Saturday links these by email: when the `email` you set on an athlete exactly matches a Saturday account's email (case-insensitive; no fuzzy matching), Saturday emails that account's verified address asking the athlete to confirm the connection to your platform, and once they confirm, the records are linked and the athlete's API responses unlock.

- **Opt in by supplying emails.** Set `email` on your athletes (`POST /v1/athletes` and `PATCH /v1/athletes/{athlete_id}`). Matching runs when you write an athlete email, when a Saturday subscription activates, and in a nightly sweep.
- **Your own key matches one address.** A key made at saturday.fit/api links only the Saturday account that made it, at its verified sign-in address.
- **You get the same webhook.** When a match links an actively paying account, `subscription.created` fires with `source: "email_match"`. Handle it like a checkout unlock.
- **Ambiguity never auto-links.** Multiple athletes sharing an email, or a conflict with an existing link, goes to Saturday-side human review instead.
- **No revenue share on matched links.** These subscriptions were not driven through your platform (many predate it), so they do not appear on your revenue statement.
- **What the match tells you.** The athlete's subscription tier, and an expiry when one applies, never payment details or purchase history. From then on the athlete's numbers are calculated from their Saturday app answers, unless their account reads as under 18; the answers themselves are returned to you only while the athlete shares them. See [Reading an athlete's fueling profile](/guides/fueling-profile).

If you have a partner-negotiated offer with Saturday (e.g. member pricing for your annual subscribers), assert eligibility by setting `partner_plan: "annual"` on the athlete (`PATCH /v1/athletes/{id}`). Eligible athletes' CTAs carry the offer claim and checkout prices accordingly. You may advertise the offer anywhere; only asserted athletes can redeem it.

### Organization (team) offers

A coach or team on your platform can have a negotiated discount. Record it on the organization (`PUT /v1/organizations/{org_id}/offer`) and assert each athlete's affiliation via `org_id`. See [Organizations: Organization offers](/guides/organizations#organization-offers-negotiated-discounts).

### How discounts stack

When an athlete qualifies for more than one discount source (a partner offer **and** an org offer), the percents combine **multiplicatively** and the total is **hard-capped at 30%**:

```
20% partner + 15% org → 1 − (0.80 × 0.85) = 32% → capped to 30%
```

Checkout collapses the stack into a single combined discount, and Saturday's subscribe landing page displays the stacked percent plus which sources contributed, so athletes see the number they will pay rather than a per-source figure.

## Testing the loop (test environment)

The test environment has a zero-payment simulator so you can integration-test your webhook handlers and tier handling end to end:

```bash
curl -X POST {TEST_BASE_URL}/v1/test/athletes/{athlete_id}/simulate-subscription \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{"active": true}'
```

The test base URL is `https://test-api.saturday.fit`.

`{"active": true}` writes the same link fields and fires the same `subscription.created` webhook as a real purchase; `{"active": false}` fires `subscription.cancelled`. The endpoint does not exist in production.

A key marks at most 10 athletes as subscribed per UTC day; marking an athlete already marked today again is free. Past that, the call returns `429` `simulated_subscriber_daily_limit_reached`, with `Retry-After` running to midnight UTC. Each simulated subscriber gets exact numbers for up to 100 answers and 3 versions of its profile; past either, answers come back in ranges with `simulated_limit_reached: true` and a `simulation_note`. Need more for a test run? Email api@saturday.fit.

You can also run a real test checkout with Stripe's `4242 4242 4242 4242` card from the CTA link in any test-env teaser response.

<Note>
  **iOS partners:** opening Saturday's web checkout from inside your iOS app is an external purchase link for digital content. Review Apple's current external-link entitlement rules for your app's situation. The CTA URL works in any browser context.
</Note>

## Attribution

Teaser data must carry the "Powered by Saturday" mark, linked, near the numbers. Full data carries a
lighter mark wherever Saturday data appears. That linked mark is how the loop closes: athletes seeing
teasers find their way to full precision through it.

Full placement rules, marks, sizing, and the per-surface matrix live on the
[Brand & Attribution](/guides/attribution) page.

## Partner value exchange

- **Partners get**: Free nutrition intelligence for their platform
- **Saturday gets**: Distribution to athletes who may subscribe
- **Athletes get**: Personalized nutrition whether they subscribe or not

More partners means more athletes seeing Saturday, and more subscribers.

<Note>
The trial starts once real profile or optional activity inputs are present. Zero-data calculations never start or burn it. Collect the [fueling profile](/guides/onboarding) and provide the per-activity inputs so trial calculations can return exact numbers.
</Note>
