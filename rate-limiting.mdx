# Rate Limiting

Saturday meters requests with a token bucket per account, not per key. Several keys on one account draw from the same bucket.

Two ceilings apply:

| Ceiling | What it bounds | Reset |
|---------|----------------|-------|
| Token bucket | Sustained rate, with a burst allowance on top | Continuous refill |
| Daily call limit | Total calls per day, on accounts that carry one | Midnight UTC |

Self-serve accounts run at 2 requests/second with a burst of 5, and 200 calls/day. Platform partner limits are set per agreement, and the platform default daily ceiling applies until one is agreed. `GET https://api.saturday.fit/v1/` states the self-serve numbers without authenticating; `GET /v1/partner` reports the limits enforced on your account.

## Rate limit headers

Every authenticated response carries the current bucket state:

```http
HTTP/1.1 200 OK
X-RateLimit-Limit: 120
X-RateLimit-Remaining: 4
X-RateLimit-Reset: 0
Content-Type: application/json
```

| Header | Description |
|--------|-------------|
| `X-RateLimit-Limit` | Sustained rate expressed as requests per minute |
| `X-RateLimit-Remaining` | Tokens left in the burst bucket right now |
| `X-RateLimit-Reset` | Seconds until the next token is available. `0` while tokens remain |

`X-RateLimit-Reset` is a delta in seconds, not a Unix timestamp. Adding it to the current time gives the moment the next request will be admitted.

## When you're rate limited

Exceeding a limit returns `429 Too Many Requests`:

```json
{
  "error": {
    "type": "rate_limit_error",
    "code": "rate_limit_exceeded",
    "message": "Rate limit exceeded. Retry after 1 seconds.",
    "documentation_url": "https://docs.saturday.fit/errors#rate_limit_exceeded",
    "request_id": "req_abc123def456"
  }
}
```

Every `429` carries a `Retry-After` header, in seconds, and a `code` that says which limit you reached. Branch on the code:

| Code | Cause | `Retry-After` | What to do |
|------|-------|---------------|------------|
| `rate_limit_exceeded` | Token bucket empty | Seconds until a token is free | Wait it out, then continue |
| `catalog_paced` | Product answers for your account have covered a large share of the product catalog in 24 hours | Seconds until new products resume | Products already answered keep working; a new product waits until `Retry-After` passes |
| `rate_limited` | An unusual request pattern, such as a sweep of calculation inputs | Seconds until the cooldown ends, up to 15 minutes | Every calculation on your account is refused until then. Requests refused with a `400` never count toward it. Contact api@saturday.fit if the traffic is legitimate |
| `daily_call_limit_reached` | Your daily call ceiling | Seconds until midnight UTC | Stop until midnight UTC |
| `intelligence_daily_limit_reached` | Your daily ceiling on intelligence endpoints | Seconds until midnight UTC | Your data endpoints keep working; calculations wait until midnight UTC |
| `athlete_free_daily_limit_reached` | Your daily budget of calculations sent without an `athlete_id` | Seconds until midnight UTC | Send an `athlete_id`, or wait until midnight UTC |
| `distinct_lookup_daily_limit_reached` | Your daily budget of distinct product lookups | Seconds until midnight UTC | Repeat lookups keep working; new ones wait until midnight UTC |

Retry `rate_limit_exceeded`, and `catalog_paced` when the wait is short. Never sleep on the four daily codes: their `Retry-After` runs to midnight UTC, so stop that work and resume after the reset.

Both SDKs do this for you. They wait out a throttle, and a pacing wait of 30 seconds or less, and retry. Everything else is raised as a rate-limit error that carries the `code`, the wait (`retryAfter` in TypeScript, `retry_after` in Python) and, for the daily codes, the reset time (`resetsAt`, `resets_at`).

<CodeGroup>

```python Python
import time

DAILY = {
    "daily_call_limit_reached",
    "intelligence_daily_limit_reached",
    "athlete_free_daily_limit_reached",
    "distinct_lookup_daily_limit_reached",
}

response = make_api_request()

if response.status_code == 429:
    code = response.json()["error"]["code"]
    wait = int(response.headers["Retry-After"])
    if code == "rate_limit_exceeded" or (code == "catalog_paced" and wait <= 30):
        time.sleep(wait)
        response = make_api_request()
    elif code in DAILY:
        schedule_after_reset(wait)  # resumes after midnight UTC
```

```typescript TypeScript
const DAILY = new Set([
  "daily_call_limit_reached",
  "intelligence_daily_limit_reached",
  "athlete_free_daily_limit_reached",
  "distinct_lookup_daily_limit_reached",
]);

let response = await makeApiRequest();

if (response.status === 429) {
  const { error } = await response.json();
  const wait = Number(response.headers.get("Retry-After"));
  if (error.code === "rate_limit_exceeded" || (error.code === "catalog_paced" && wait <= 30)) {
    await new Promise((r) => setTimeout(r, wait * 1000));
    response = await makeApiRequest();
  } else if (DAILY.has(error.code)) {
    scheduleAfterReset(wait); // resumes after midnight UTC
  }
}
```

</CodeGroup>

Athlete-delegated callers (OAuth2 and the Saturday connector) also pass through a per-athlete bucket inside the account's bucket, so one heavy user cannot starve the rest. Those 429s carry a longer `Retry-After`. See [OAuth2](/guides/oauth2).

## Daily call limits

Alongside the token bucket, every account carries daily call ceilings:

| Account | Daily ceiling |
|---------|---------------|
| Self-serve | 200 calls/day |
| Partner, no agreed ceiling | Platform default, 2,000 calls/day |
| Contracted integration | Per agreement, up to no ceiling at all |

Intelligence endpoints (nutrition calculations, prescriptions and prep, product fit and compare, calculations asked for at import, inference, knowledge, AI) also carry a separate daily ceiling, apart from the total. Data endpoints (your athletes, activities, organizations, webhooks) are not counted against it, so hitting the intelligence ceiling never blocks syncing your data.

Each request to the [MCP endpoint](/guides/mcp-integration) counts once toward the daily ceiling, a tool call included; a tool that calculates, sizes products or infers also counts once toward the intelligence ceiling.

Without an agreed intelligence ceiling, your budget grows with your day: a base allowance plus a per-athlete allowance for every athlete you compute for that day. Integrations serving real athletes scale automatically; if your traffic pattern needs more than the budget provides, contact api@saturday.fit.

Two daily budgets bound a few surfaces. Distinct product lookups and distinct search queries are capped (`distinct_lookup_daily_limit_reached`), and repeats always serve, so a real workload (your athletes' usual products, revisited) never feels it; enumeration does. Calculations that carry no `athlete_id` have their own budget, 50 a day by default (`athlete_free_daily_limit_reached`), and every one counts, repeats included; calculations for your athletes are unaffected.

Reaching any daily ceiling or budget returns `429` with the code from the table above and a `Retry-After` of the seconds until midnight UTC, when the counters reset; the message names the limit. `GET /v1/partner` reports the ceilings that apply to your account (`rate_limits.requests_per_day` and `rate_limits.ip_requests_per_day`, `null` when none applies). To raise yours, contact api@saturday.fit.

## Staying under the ceilings

### Spread requests out

The burst allowance covers a short spike, then refills at the sustained rate. Pacing requests across the window keeps the bucket from emptying; draining the burst up front means every subsequent request waits.

### Cache prescriptions

A prescription for the same inputs is stable. Cache the result and recalculate when:

- The athlete's profile settings change
- Activity parameters change, such as an updated duration or a new weather forecast
- You want a fresh calculation for race day

### Use the batch endpoint

```bash
POST /v1/nutrition/calculate/batch
```

Each item in a batch debits a token, so a batch of 10 costs what 10 calls cost. What it saves is round trips, not quota. See [Batch Operations](/guides/batch-operations).

### Watch your usage

```bash
curl https://api.saturday.fit/v1/partner/usage \
  -H "Authorization: Bearer $SATURDAY_API_KEY"
```

`GET /v1/partner/usage/daily` breaks the same counters down by day.

## Requesting higher limits

Outgrowing the ceilings is the point at which we want to hear from you. Send your account or partner ID and expected volume to [api@saturday.fit](mailto:api@saturday.fit). Raising a limit costs nothing.
